    架构定位与业界对标¶

    回答一个问题：本系统的架构（脚本确定性循环 + LLM 无状态判断 + 外置文件记忆）在公开的智能体架构世界里处于什么位置。 成文于 2026-11-09，基于实盘首日验证后的架构定稿（见 直播监控方案.md）。

    一句话定位¶

    本系统属于 「确定性工作流（workflow）+ 无状态 LLM 节点 + 外置文件记忆」 模式——与 Anthropic 的 workflow 类别、LangGraph 的 checkpointer 理念、n8n/Zapier 的 AI 节点管道同构；且 2025→2026 业界正整体从「自主循环 agent」回潮到这种结构化模式。

    逐项对标¶

    本系统设计 公开相似架构 相似度
    Python 确定性循环驱动（monitor_poll），LLM 只做判断不做调度 Anthropic《Building Effective Agents》的 workflow 类别（代码编排 LLM 调用，区别于 LLM 自主循环的 agent）；2026 企业编排指南的 deterministic backbone（确定性主干） 模式完全同构
    每批消息一个独立 LLM 任务、全新 session-id、进程级隔离 n8n / Zapier 的「触发器 → AI 步骤 → 动作」管道；prompt chaining 同构；本系统隔离更彻底（每任务一个进程，结束即消失）
    状态全部外置文件（messages/pushes/state.json + 哈希去重），模型会话刻意不用 LangGraph 的 checkpointer（图状态外置持久化、可恢复重跑）；Letta（原 MemGPT）的 external memory 理念 理念相同；本系统用纯 JSONL，不依赖框架
    脚本管工具与副作用（重试/自愈/落盘），LLM 经 Bash 间接执行 Claude Code / traecli 的 harness 概念（确定性外壳管工具/权限/循环，LLM 管决策）——本系统等于自建了一个 mini-harness 同构
    验证码人机接力（sms_code.txt 轮询 + make auth-input-code） HITL（human-in-the-loop）interrupt 模式（LangGraph interrupt、工作流引擎的人工审批节点） 同构
    常驻自主循环（legacy-agent，2026-11-09 删除，git 可溯） browser-use、LangChain AgentExecutor 等大量「LLM 自主循环」框架——正是实测不可靠后主动退出的那条路 走过又退回的岔路

    与典型方案的两个差异¶

    1. 零框架：LangGraph/n8n 用户靠框架获得的东西（状态外置、确定性边、重试），本系统用 13 个脚本 + JSONL 直接实现。代价：没有可视化编排界面；收益：零依赖、每行可审计、行为完全可预测。
    2. LLM 节点本身是一个完整 agent：典型工作流的 AI 节点只做一次纯模型调用；本系统的节点是 traecli exec——一个能读文件、执行 Bash、自己调推送脚本的 coding agent。相当于确定性工作流里嵌了一个 agent 作为超级节点。这是与 n8n 类方案最大的能力差异：分类判断时它能自己去读 memory.md 分类体系全文，而不只吃 prompt 内嵌的定义。

    为什么走到这里（决策依据）¶

    1. 常驻 agent（traecli 循环会话）实盘实测：轮询正常但推送环节失效，过程输出不可见、resume 并发静默——LLM 自主循环的可靠性不满足 7×24 无人值守要求；
    2. 退回确定性工作流后：重试/去重/自愈/落盘全部回到脚本层，故障可观测（每步有日志与档案），当日即恢复稳定运行；
    3. 这条路径与业界结论一致：2026 年企业实践（如 Azure 架构中心的 AI agent 编排模式 一派）明确主张用确定性主干换取成本、治理与可靠性，把 LLM 的自主性收敛到明确边界的判断节点里。

    结论¶

    本系统没有发明新架构，而是用最朴素的方式走到了业界正在回潮的位置：从「让 LLM 自己循环盯盘」退回到「脚本管可靠、LLM 管判断、档案管记忆」。模式公开且成熟，独特之处在组合细节：进程级单次任务隔离、先归档后处理、双去重、失败重试与补推链、以及「完整 agent 作为工作流节点」的嵌套用法。
